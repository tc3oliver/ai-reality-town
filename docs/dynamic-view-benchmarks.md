# Dynamic Viewing Benchmark (FR-Q005 / ART-136, implementing NFR2-002)

The specification. The recorded figures live beside it in `docs/benchmarks/`, regenerated by
`npm run bench` and committed as evidence (AC#11).

Related: `docs/dynamic-view-e2e.md` (the build and fixture this runs against),
`docs/dynamic-view-degradation.md` (the four modes), `docs/dynamic-view-observability.md`
(the server-side metrics that cover what a fixture cannot).

## 1. Running it

```bash
npm run bench                     # build:e2e → bench:run → bench:report
BENCH_SOAK_MINUTES=480 npm run bench    # the eight-hour soak NFR2-002 asks for
BENCH_SOFTWARE_GL=1 npm run bench       # force software rasterisation
```

`bench:report` exits non-zero when any measured criterion fails, so the benchmark is usable as
a gate and not only as a report. Criteria recorded as `requires_deployment` or `unreachable` do
**not** fail the run — they are gaps this harness has stated, and turning a stated gap into a
red build is how the statement gets deleted.

## 2. What makes it a benchmark rather than a set of timings

Three things, and all three are in the **output**:

- **A named device profile with a fixed CPU throttling factor** (AC#8). `desktop-reference` at
  1440×900 unthrottled, and `mid-tier-mobile` at Pixel 5's viewport and device scale with a 4×
  CPU slowdown — the factor Chrome's own "Mid-tier mobile" preset uses, so it is an industry
  reference point rather than a number invented here.
- **The browser version and the GL renderer.** Two runs on different Chromium builds are not
  comparable, and the difference between a hardware and a software rasteriser is worth roughly
  everything to a frame rate. The renderer is read from the page rather than inferred from the
  launch flags: `--ignore-gpu-blocklist` is a *request*, and a host with no usable GPU silently
  falls back to SwiftShader anyway.
- **A fixed camera zoom** (AC#9), set by returning to the town view before sampling.

## 3. The four modes (AC#10)

| Mode | How it is produced |
|---|---|
| `stream` | The ordinary page |
| `delayed` | Fixture serves a runtime snapshot whose **content** is seven hours old while the capture path still confirms it — `classifyRuntimeFreshness` calls that `delayed`. Ageing `observedAt` instead would give `stale`, a different state |
| `snapshot` | Fixture returns `null` for the dynamic projection, which is exactly what the real query returns when the read-model store has nothing left to serve |
| `degraded` | WebGL denied in the browser by overriding `getContext` before any application code runs |

`degraded` needs no product hook. `delayed` and `snapshot` are facts about what the **server**
returned and cannot be produced from the browser at all, so they come from a scenario knob
inside `src/e2e/` — the module production reaches through exactly one import behind one
build-time literal. `fixtureScenario.test.ts` pins that no shipped file imports it and that it
never becomes a second gate.

`snapshot` was not measurable before ART-127: the live map had no code path that read the
runtime snapshot.

## 4. The metrics, and why there are three frame-rate figures

- **Time to interactive** (AC#1) — navigation start to the first control being operable, not
  `load`. A page that has fired `load` while Pixi is still compiling shaders is not interactive.
  Measured against a control that exists at every rung, so the definition does not quietly
  change between modes.
- **Average FPS** (AC#4) — the headline.
- **P5 FPS** — sustained choppiness. With 120 frames, one 400ms hitch is the worst 0.8% and P5
  correctly reports 60; P5 is the figure for "the viewer spent real time watching it stutter".
- **Worst FPS** — the single slowest frame, and the only one of the three that sees a lone
  stall. One 400ms freeze is what a viewer calls "it froze", and neither the mean nor the
  percentile shows it.
- **Heap growth** (AC#7) — see below.
- **Semantic stability** (AC#5) — the same four characters read at 1× and 6× CPU, through the
  **card**, because the claim worth making is about what the product says rather than about a
  field nobody sees. `motionQualityTiers.test.ts` already proves it of the pure function; this
  proves it of the whole path in a real engine.

## 5. Heap growth is measured on the post-collection floor

The first implementation fitted a least-squares line to the raw heap samples. That is wrong in
a way that looks right: every JS heap sawtooths, and a regression over a sawtooth does not
return zero unless the cycles happen to align with the sample window. A perfectly healthy page
cycling 40→70 MiB reported nearly **3 MiB/min of "growth"** purely from where its cycles fell —
enough to fail AC#7 on a page with no leak at all. Raising the threshold until that stopped
would have been fitting the gate to the noise.

What distinguishes a leak is that the heap does not come back **down** as far as it did before.
So the run is split into six time windows, the minimum of each is taken — the post-collection
floor — and the trend is measured across those. `measure.test.ts` pins both directions: a
constant-amplitude sawtooth reads as zero, and the same sawtooth with a rising floor is caught.

"Last minus first" is wrong for the same underlying reason and in both directions: a run ending
just after a collection reports negative growth while leaking, and one ending just before
reports a large positive while healthy.

## 6. What this harness cannot settle, stated rather than dropped

A gate that silently drops what it cannot measure reports green for a system nobody measured,
which is worse than reporting a gap because it looks like evidence. These appear in the results
file with a status and a reason.

### `requires_deployment`

- **AC#2, public dynamic query P95.** The E2E build replaces the **transport** with a
  synchronous in-process fixture. Measuring it here records ~0ms and prints a pass for a path
  that was never exercised.
- **AC#3, runtime-to-screen latency.** Spans the simulation, the projection rebuild and the
  subscription push, none of which exist in a fixture build. ART-133 already publishes the
  server half as the `runtimeProjectionLatency` metric; the end-to-end figure belongs to
  ART-138.

### `unreachable` — twenty and forty visible characters (AC#6 / AC#9)

Mistwood has exactly twelve residents. `MISTWOOD_CHARACTER_VISUALS` holds twelve,
`mistwoodCharacterSpriteKeys` is derived from it, `mistwoodCharacters.test.ts` pins the roster
against `buildMistwoodCharacterVisualBindings()`, and `composeReadOnlyWorldViewModel` **drops**
any character with no visual binding because FR-N004 AC#6 requires an unbound character to be
rejected rather than silently reskinned.

So twenty and forty are not "not yet measured" — they are not representable in this world
without breaking one of those two guarantees. The harness takes the count as a parameter, so
the criterion becomes measurable the day a world has more residents. Inventing twelve extra
bindings to make a number appear would be measuring a world that does not exist, which is
exactly what the fixture rule (ART-107 §8) forbids.

### `measured_but_inconclusive` — mobile frame rate

**The mobile profile currently fails AC#4, and the failure is reported as a failure.** The
recorded figure is ~27 fps average against a 30 fps threshold.

The context, which does not exempt it: this host has no usable GPU. Chromium reports an
ANGLE/SwiftShader device even with the GPU blocklist ignored, so the mobile profile
software-rasterises a 1080×2340 backing store — roughly twice the desktop profile's pixels —
while also under 4× CPU throttling. That is a harsher environment than the named device, and
the figure therefore cannot settle the criterion either way for real mobile hardware.

Both halves are recorded: the number stands as a fail, and the reason it is inconclusive stands
beside it. An authoritative mobile figure needs a device, which is ART-138's job. Notably the
`degraded` rung reaches 60 fps on the same profile, which locates the cost in the Pixi stage
rather than anywhere else on the page.

## 7. The eight-hour soak

`BENCH_SOAK_MINUTES` defaults to 2 so `npm run bench` stays usable. The committed result is a
short run, and it is evidence that the harness can **detect** growth — not evidence that an
eight-hour run is clean. The eight hours NFR2-002 asks for is an operator step at the release
gate, set with the same knob.

## 8. What ART-136 does not own

`activeViewerCount` (`docs/dynamic-view-observability.md` metric #3) is listed there with
ART-136 as owner. It is not built here, and deliberately: collecting it requires the browser to
**report**, which is a client write, and `readOnlyClientBoundary` forbids every client write
primitive. That makes it an external-analytics-sink concern, which is FR-Q007's territory
(ART-140), and the observability doc already says so in the same breath.
